01 / PRODUCT PROBLEM

Physical access is a permission system disguised as a door interaction

The concept reframes access control from isolated hardware into a permission layer: people have identities, identities receive credentials, credentials inherit scoped access to buildings, doors, floors and time windows. That model connects the employee arrival experience with the security administrator’s need for control and auditability.

People needEnter without ceremonyRoutine access should not feel like repeated authentication work.
Security needKnow who can enter wherePermission, expiry and revocation need one inspectable model.
Enterprise needConnect identity systemsPhysical access should reflect directory and employment changes.
Evidence statusPrototype verifiedFlows and states exist; real facility behavior is not measured.
CLAIM BOUNDARY

ACCESS is an independent product concept. Hardware behavior, directory sync, compliance and accessibility language in the prototype are product/design targets unless independently validated. No facility deployment, security certification, penetration test or customer outcome is claimed.

02 / PRODUCT MODEL

One permission chain connects mobile convenience to enterprise control

01Person

Employee, visitor, contractor or de-provisioned staff member.

02Identity + credential

A trusted identity receives a mobile pass, QR credential or other access method.

03Scope + time

Permission maps to site, door, floor, role and expiry window.

04Decision at entry

Grant, deny, expire, revoke or lockdown with an explainable system state.

03 / JOURNEYS + STATES

The product has to support routine entry and exceptional security moments

The working prototype spans cloud access control, mobile access, visitor management, enterprise governance, integrations and a demo journey. The strongest system decision is to keep normal access, guest expiry, de-provisioning and emergency lockdown within the same permission language.

EmployeeMobile credentialLow-friction daily access with visible credential state.
VisitorScoped temporary passPre-register → verify → check in → host notification → auto-expiry.
AdminCentral permission controlSites, roles, zones and revocation remain inspectable.
EmergencyLockdown stateExceptional control is explicit rather than hidden in settings.
04 / TRADE-OFFS

Frictionless does not mean invisible security

SelectedProgressive disclosure

Everyday users see credential status and the next action; deep policy stays with administrative contexts.

SelectedNon-color status cues

Labels and icon/state language support interpretation beyond green/red signals.

SelectedCredential revocation as first-class state

Lost devices and de-provisioned staff are product journeys, not implementation footnotes.

GuardrailConvenience cannot bypass authority

Faster entry still needs scoped identity, permission and expiry rules.

05 / VALIDATION GAP + NEXT TEST

The next pass should test comprehension with people who operate real buildings

No security-operator interviews, visitor observations or real hardware tests are available in this repository. The next evidence should therefore focus on whether the permission model is understandable under both normal and urgent conditions.

Task 01Revoke a lost credential

Can an admin identify the person, credential and consequence without ambiguity?

Task 02Trace a visitor permission

Can a security operator explain where a guest can go and when access expires?

Task 03Enter lockdown

Can the operator understand scope, confirmation and recovery before committing?
