FINANCIAL DECISION UX · SAFE-TO-SPEND · RECOVERY

Nova

A personal-finance concept built around one question: what money is actually safe to spend after upcoming obligations and a protected buffer?

01 / CONTEXT + PROBLEM

Balance is a number. Spending safety is a decision.

Nova is a self-initiated responsive banking prototype for digital-first account holders who manage recurring payments and day-to-day spending. The design problem is narrower than “redesign mobile banking”: an account can show a positive balance while still hiding commitments that make part of that money unsafe to spend.

User problemAvailable ≠ safely spendableUpcoming commitments change the meaning of today’s balance.
Product riskFalse confidenceA visually optimistic balance can support a poor spending decision.
Critical journeyReview → protect → recoverUnusual transaction through freeze and recovery.
Evidence statusNo measured outcome yetBenchmark-informed hypothesis + implemented prototype.
PROJECT REALITY

Nova is not a bank and does not move real money. Balances, Money Horizon calculations, risk flags, KYC, biometrics, transfers and notifications are simulated prototype states. No conversion, retention, loss-prevention or usability improvement is claimed.

02 / PRODUCT THESIS

Bring future obligations into the decision surface

Hypothesis: if current balance, known commitments, planned savings and a protected buffer are presented together as a forward-looking Money Horizon, users may be able to make everyday spending decisions with less uncertainty.

Target userDigital-first account holder

Recurring bills, subscriptions and active day-to-day spending.

JTBDKnow what is safe before acting

Understand near-term obligations before spending or transferring money.

Business goalTrust before engagement

Future product value should come from clearer financial decisions, not simply more taps.

Non-goalPredict the future perfectly

The prototype makes assumptions visible instead of presenting a forecast as certainty.

Product principles

01Future before optimistic balanceKnown obligations affect available-money interpretation.
02Explain before commitmentTransfers expose impact before confirmation.
03Protection must be recoverableFreeze is paired with visible recovery routes.
04Status cannot rely on colorMoney and risk states use labels and structure beyond hue.
03 / BENCHMARK → DECISION

Research matters when it changes the interface

Benchmark: Monzo’s Trends guidance describes “left to spend” as an estimate influenced by upcoming payments. Nova does not copy that UI; the transferable pattern is that future commitments belong in spendability logic rather than a disconnected calendar.

BENCHMARK PATTERN

Upcoming payments influence what remains to spend.

INSIGHT

A present-day balance is incomplete decision context.

DESIGN DECISION

Money Horizon groups projected balance, upcoming events and protected buffer in one planning surface.

LIMIT

This supports a pattern, not Nova’s usability. Direct testing is still required.

04 / ALTERNATIVES + TRADE-OFFS

The selected direction adds context without turning home into a spreadsheet

Option A · rejectedBalance-first dashboard

Fast to scan, but keeps upcoming obligations secondary and preserves the original ambiguity.

Option B · selectedBalance + Money Horizon

Pairs immediate money state with a compact forward view and explicit buffer.

Option C · rejected for homeFull cash-flow planner

More detail, but creates cognitive and interaction cost before a user asks for planning depth.

Trade-offRichness vs loadForecast context is visible; detailed controls stay progressive.
Trade-offSpeed vs safetyTransfers add review so impact is visible before commitment.
Trade-offProtection vs frictionFreeze is prominent, but recovery remains equally explicit.
Trade-offConfidence vs certaintyForecasts are planning context, not guaranteed outcomes.
05 / COMPLEX FLOWS + RECOVERY

The case is strongest when the happy path breaks

Risk flowUnusual transaction → detail → freeze

Evidence and consequences precede the protective action.

Transfer flowRecipient → amount → review → auth → result

Impact is reviewed before the simulated transfer completes.

RecoveryFreeze ↔ unfreeze

The protective action is reversible through an explicit state.

Exception setInsufficient funds · offline · KYC retry

Correction, retry and manual-review concepts are designed rather than omitted.

These are prototype states that demonstrate systems thinking. They are not evidence that real customers completed them successfully.

06 / SYSTEM + DELIVERY

Design intent stays connected to implementation

The project separates product context, user flows, sitemap, component states, implementation and QA. The prototype targets 1440 / 1024 / 768 / 390 and uses static HTML/CSS/JavaScript so the interaction model remains inspectable without pretending a production backend exists.

DesignFlow + state contractsSitemap, user flows and state artifacts define behavior.
CodeImplemented prototypeResponsive UI and simulated states are inspectable.
A11y targetWCAG 2.2 AA behaviorsTouch targets, focus, reduced motion and non-color status cues.
QABrowser evidence requiredBuild success alone is not treated as visual correctness.
ENGINEERING REALITY

Static front-end and simulated finance operations are prototype constraints. Production would require ledger data, authentication, fraud/risk services, security review, privacy controls, regulatory requirements and failure handling beyond this concept.

07 / VALIDATION + METRICS

What I would measure before claiming improvement

Research objective: test whether people correctly interpret Money Horizon and can act on it without mistaking forecasted or committed money for immediately spendable funds.

Task 01Safe to spend before Friday

Determine the amount and explain which obligations changed the answer.

Task 02Review an unusual transaction

Inspect context, protect the account and recover if the freeze was accidental.

Task 03Send money safely

Explain the effect of a transfer before confirming it.

Task 04Recover from failure

Resolve insufficient funds, offline review or authentication fallback.

Primary target metricTask successPlanned, not measured.
Secondary targetsTime · errors · confidenceUse the same tasks before and after iteration.
Product targetMoney Horizon adoptionFuture measurement if instrumented.
Guardrail targetDecision / recovery errorsDo not trade speed for harmful mistakes.
08 / WHAT NEXT

The most important parts remain deliberately unvalidated

REMAINS UNVALIDATED

Whether Money Horizon reduces uncertainty, whether the forecast is understandable without explanation, whether protective actions create excessive friction, and whether the mobile hierarchy holds under real personal-finance data.

Next: run a baseline test on the current prototype, prioritize interpretation failures over visual preference, iterate the model and labels, then repeat the same tasks. With real engineering/data access, validate forecast assumptions, notification timing, transaction data quality and the relationship between confidence, errors and feature adoption.
