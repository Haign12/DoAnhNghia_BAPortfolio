# All-project recruiter proof system

Purpose: make product-design capability inspectable in 30–60 seconds without calling the designer “senior”. This document is the canonical copy/spec for the 14 selected portfolio projects.

Evidence labels are strict:
- `VERIFIED` = backed by direct repository/runtime/research evidence.
- `DIRECT_USER_ASYNC_SELF_REPORT` = participant self-report; not moderated observation.
- `TECHNICAL_PROOF` = source/build/browser/QA evidence; not user outcome.
- `PLANNED / NOT MEASURED` = target exists, no direct-user baseline yet.
- `OPEN` = unresolved product/evidence gap.
- `[ĐIỀN SỐ THẬT]` = do not publish as a number until traceable evidence exists.

## BƯỚC 1 — Audit nhanh

### P1 — ảnh hưởng trực tiếp tới niềm tin recruiter

1. **Most cards expose capability nouns, not proof.** Labels such as “Complex IA”, “Commerce IA”, “Art direction” and “Systems thinking” describe intent but do not show evidence state.
2. **Direct-user evidence is concentrated in Nova.** The other selected product cases have measurement targets, but direct-user baselines are still `PLANNED / NOT MEASURED`.
3. **Nova source-of-truth was stale in supporting registries.** Round 02 is complete, but older audit/measurement copy still says retest pending.
4. **Some projects look more complete than the evidence actually is.** Live/Figma/source links prove delivery artifacts, not research validation or business impact.
5. **Prototype “design lens” is not consistently visible.** Decision IDs, before/after, unresolved findings and state-risk callouts are not yet standardized across projects.

### P2 — recruiter can miss the product-design depth

1. Hero images mostly show polished outputs, not before→after or decision causality.
2. Case-study scanning is uneven: not every case starts with Problem → Decision → Evidence → Change → Retest → Still open.
3. Project links say “Case / Live / Figma” but not what a reviewer will verify at each destination.
4. State/edge-case depth exists in several prototypes but is not consistently surfaced as a proof layer.

### P3 — cleanup / consistency

1. `CENNEXT` vs `G.I.E` naming should be explained once and then kept consistent.
2. LUMEN and HUẾ have no published Figma link in the current audit.
3. Internal artifact-maturity levels must remain internal and must never become public “senior scores”.

## BƯỚC 7 — Nên tránh

| Avoid | Replace with |
|---|---|
| “Senior UX / senior-level project” | Concrete evidence: `2 rounds`, `state/recovery coverage`, `decision log`, `retest`, `open findings`. |
| “Validated” when only QA/synthetic review exists | `TECHNICAL_PROOF VERIFIED` or `SYNTHETIC/DOGFOOD`, whichever is true. |
| “Tested with users” for an async form without context | `5 direct-user async self-report records` or the exact method. |
| “Usability improved” without compatible pre/post observation | `Round 02 produced new post-change evidence; causal improvement not claimed.` |
| “Business impact” on independent concepts | `Outcome target` / `business hypothesis` / `impact not measured`. |
| “Research shows…” when evidence is desk/AI | `Desk evidence suggests…` or `Hypothesis to test…`. |
| “Fully accessible” after basic axe/browser checks | `Accessibility basics checked with [tool/scope]; manual audit not claimed.` |
| “Production-ready” for a portfolio prototype | `Working prototype` / `implementation proof` / `QA-verified in tested scope`. |
| Generic `Senior signals` | `Product-design evidence` + exact evidence state. |
| `[ĐIỀN SỐ THẬT]` on a public page | Keep placeholder internal until verified, then publish the number and source. |

## Publish checklist — 10 điểm

- [ ] Problem is one decision/problem, not a product description.
- [ ] Every numeric claim has a traceable source.
- [ ] Evidence class is explicit: synthetic / desk / hypothesis / direct-user / moderated / retest / technical proof.
- [ ] No async response is relabeled as moderated usability observation.
- [ ] Card shows what changed because of evidence — or explicitly says no direct-user change claim yet.
- [ ] Decision/state chips include status: fixed / partially fixed / open / planned.
- [ ] Primary CTA tells the recruiter what they will verify.
- [ ] Case intro follows Problem → Decision → Evidence → Change → Retest → Still open.
- [ ] Prototype exposes important decisions/states, not only happy-path screens.
- [ ] Open findings remain visible; no “success story” overwrites contradictory evidence.
